# Антифрод-система «Страхование жизни и аннуитеты»

Выявление мошеннических схем по пенсионным аннуитетам (ПА), аннуитетам ОСНС и накопительному страхованию жизни (НСЖ).
Требования — в [docs/PRD.md](docs/PRD.md). Текущий этап — **MVP**: один пользователь, локальный запуск, SQLite.

## Что есть

- **Витрина дел** (`cases`) по полям из PRD 5.1, импорт CSV/XLSX с отчётом о загрузке.
- **Движок правил**: 18 правил, по модулю на каждое (`backend/app/rules/`), единый интерфейс
  `evaluate(case, context, params) -> объяснение | None`. Пороги и веса хранятся в таблице `rules`
  (сид — стартовые значения из PRD 6.2). Ошибка в правиле не останавливает прогон.
- **Скоринг**: сумма весов, не больше 100; уровни «высокий» от 50 и «средний» от 25 (настраиваются).
  Каждый прогон сохраняет версию и снимок набора правил, поэтому результат воспроизводим.
- **Веб-интерфейс** (`/`): сводка, очередь с фильтрами, карточка дела со статусом и историей, агенты,
  редактор правил с историей изменений, калибровка, импорт и экспорт, журнал действий. Светлая и тёмная темы.
- **API** (FastAPI): документация на `/docs`.

## Запуск

Нужен Python 3.12+.

```bash
cd backend
python -m venv .venv
.venv\Scripts\activate          # Windows; на Linux/macOS: source .venv/bin/activate
pip install -r requirements-dev.txt
uvicorn app.api.main:create_app --factory --reload
```

Откройте http://127.0.0.1:8000. База создаётся в `data/antifraud.db` (папка `data/` не попадает в git).
Другая БД задаётся переменной `DATABASE_URL`, например `postgresql+psycopg://user:pass@host/antifraud`
(для PostgreSQL установите драйвер `psycopg[binary]`).

Через Docker:

```bash
docker compose up --build
```

## Демо на GitHub Pages

Адрес: https://marat16051979-spec.github.io/-/

Сервера у демо нет. Тот же Python-код движка и API (`app/api/handlers.py`) работает прямо в браузере
через [Pyodide](https://pyodide.org) (`app/demo_bridge.py`, `app/static/demo.js`), а база — SQLite в памяти вкладки.
При открытии загружаются вымышленные данные из `sample.csv`. Изменения видит только сам посетитель,
и они сбрасываются при перезагрузке страницы. Первый запуск занимает 5–15 секунд.

**Не загружайте в демо реальные данные клиентов.** Сам файл не уходит в интернет, но страница
публичная, а Pyodide загружается с внешнего CDN. Это противоречит требованиям PRD о размещении
во внутреннем контуре.

Публикация: GitHub Actions (`.github/workflows/pages.yml`) при каждом push в `main` прогоняет тесты,
собирает сайт (`python backend/tools/build_pages.py _site`) и публикует его. Один раз нужно включить:
Settings → Pages → Build and deployment → Source: **GitHub Actions**. На бесплатном тарифе GitHub Pages
работает только для публичных репозиториев.

Проверить демо локально:

```bash
python backend/tools/build_pages.py _pages_preview/-
python -m http.server 8001 --directory _pages_preview
```

и открыть http://localhost:8001/-/?demo=1.

## Загрузка данных

1. Вкладка **Данные** → выберите CSV или XLSX → **Загрузить**. «Заменить витрину» удаляет прежние дела,
   «Дополнить» добавляет или обновляет дела по `id`. Статусы и комментарии по делам сохраняются.
2. Формат: первая строка — названия полей из PRD 5.1 (`id`, `product`, `client`, …). Можно использовать
   и русские подписи полей из шаблона. Разделитель `;` или `,`, кодировка UTF-8 (с BOM или без), запасной
   вариант — Windows-1251. Обязательны только `id` и `product`; лишние столбцы пропускаются и попадают в отчёт.
3. Значения: даты `ГГГГ-ММ-ДД` или `ДД.ММ.ГГГГ`; логические `1/0`, `да/нет`, `true/false`; суммы можно
   писать с пробелами и запятой. Пустая ячейка означает «нет данных», и правило по такому полю не срабатывает.
4. Пустой шаблон: кнопка «Шаблон CSV» или `GET /api/import/template`.
5. Номера карт и счетов загружайте только в виде маски или хэша (`payerCard`).

Пакетная загрузка без интерфейса (например, ежедневно по расписанию):

```bash
cd backend
python -m app.cli load путь/к/выгрузке.csv
python -m app.cli run
```

Демо-набор: `backend/tests/fixtures/sample.csv`: 75 вымышленных дел, из них 25 подставленных случаев из PRD, раздел 11.

## Тесты

```bash
cd backend
pytest
```

- `tests/test_rules.py` — каждое правило: срабатывание, граница, пустые поля; скоринг, отключение правил, ошибки.
- `tests/test_acceptance.py` — критерии приёмки PRD 11 на `sample.csv`.
- `tests/test_importer.py` — CSV/XLSX, разделители, кодировки, лишние столбцы, битые строки.
- `tests/test_api.py` — очередь, карточка, статусы, пересчёт при смене веса и порога, история, экспорт, аудит.

Чтобы пересоздать демо-набор: `python tests/fixtures/generate_sample.py` (генерация детерминирована).

## Решения и отступления от PRD

- **Интерфейс без сборки.** В MVP это статические HTML/JS, их отдаёт FastAPI, Node.js не нужен. Переход на
  React + TypeScript + Vite запланирован на v1 вместе с ролями и SSO.
- **БД.** В MVP используется SQLite и `create_all`. В v1 — PostgreSQL 16 и миграции Alembic.
- **Дата отсчёта окна A2** — самая поздняя дата договора в витрине, а не «сегодня». Так прогон на одних и тех же
  данных всегда даёт одинаковый результат.
- **Случай «5 договоров одного ТОО» в sample.csv.** У одного N1 вес 20, то есть «низкий» уровень, а PRD ожидает
  «средний». В демо-наборе премии за всех пятерых платит работодатель с одного счёта. Это типично для зарплатной
  схемы, поэтому срабатывает ещё и N3, и уровень получается «средний». Нужно решить, повышать ли вес N1 до 25+.
- **Очередь** фильтруется в памяти. Для 500 тыс. дел в v1 фильтрацию нужно перенести в SQL с индексами.

## Ограничения MVP

Нет ролей и аутентификации (пользователь `local`, можно передать заголовок `X-User`), выплаты не блокируются
автоматически, интеграции с АФМ и внешними регистрами нет. Всё это — этапы v1 и v2 в PRD.

Все пороги — стартовые значения для калибровки, а не нормы регулятора. Перед внедрением сверить с действующими
редакциями актов РК и постановлениями АРРФР.
